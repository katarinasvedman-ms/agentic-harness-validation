Why governance changes

Agents act, not just answer.

Agents can plan, call tools, use data, and change systems. At enterprise scale, that creates three immediate problems: an estate that drifts, actions that are unsafe or opaque, and capabilities rebuilt in silos.

Inventory drift

Teams create agents faster than central teams can track them. Unknown agents create unknown risk.

Duplicated capability

Many agents repeat the same tools, prompts, and workflows because there is no certified reuse path.

Runtime opacity

Without traces across prompts, policy, tool calls, approvals, data access, and outcomes, governance becomes manual archaeology.

One memorable governance model

Visibility surrounds the estate. Control meets the action. Evidence closes the loop.

Portfolio governance and runtime enforcement work together but remain distinct: the portfolio establishes ownership and acceptable risk; the checkpoint decides whether this exact action may proceed.

Runtime enforcement

Design-time review is not enough for agentic systems.

Portfolio governance establishes ownership and risk. Runtime enforcement separately evaluates the exact action before a side effect, close to the tool or operational system and independent of model self-authorization.

RequestUser or workflow trigger

Authenticated user, business process, or scheduled event.

ReasonAgent runtime

Model, prompt, memory, retrieval, planning, and tool selection.

CheckPolicy and guardrails

Agent ID, safety, DLP, data boundaries, jailbreak checks, and action policy.

ApproveHuman or automated gate

Exact approval for high-impact actions, budgets, and exceptions.

LeaseTask-scoped authority

Mint short-lived, single-use authority from verified structured intent, never from prompt wording alone.

ExecuteEnforcement point

Revalidate Agent ID, scope, policy, approval, lease, and audit before side effects.

Runtime enforcement should be close to the side effect. If a tool can change a system, the enforcement point must re-check Agent ID, authorization, policy, approval, the exact task-scoped lease, and blast radius even if the agent already checked earlier. In the local proof point, the lease is an application authorization artifact, not an Entra token or dynamic Azure RBAC grant.
Response & Recovery

Containment is layered, and restoration is an authorized workflow.

There is no universal stop button across every agent and runtime. Agent 365 provides a central governance surface for supported management actions, while identity, gateway, hosting, endpoint, data, and application controls enforce the response within their own boundaries.

Contain the smallest effective scope

  • Block an agent or active instance through Agent 365 where the platform supports that action.
  • Disable the Entra Agent ID or revoke downstream session and token access.
  • Block or throttle model, API, tool, MCP, and agent traffic through APIM or another gateway.
  • Quarantine the network path, suspend the runtime, or terminate the process when lower-impact controls are insufficient.
  • Use the application containment gate to prevent new governed side effects immediately.

Restore trust in stages

  • Re-attest identity, code, configuration, policy, and the known-good deployment version.
  • Record root cause, remediation, accountable owner, and recovery authority.
  • Restore read-only investigation before write-capable operation.
  • Observe the restricted agent and require explicit sign-off before expanding access.
  • Close the audit trail by linking containment, remediation, re-enrollment, and outcome evidence.

Evaluation and observability

Trust is maintained through continuous evidence.

Release evidence, correlated runtime telemetry, and post-change regression results show whether controls continue to work. Formal proof claims apply only to bounded deterministic plan checks—not to the whole agent.

Inventory and ownership

Knowing what agents you have requires both registration and detection.

Microsoft Agent 365 Agent Registry is the first inventory surface. Telemetry, connected platforms, and gateway logs then help reconcile what is registered, unmanaged, ownerless, active, risky, or missing.

Minimum agent passport

  • Business owner, technical owner, and support contact.
  • Purpose, users, environment, lifecycle state, and value hypothesis.
  • Entra Agent ID, model/provider, data sources, tools, and permissions.
  • Risk tier, required approvals, eval suite, guardrails, and audit retention.
  • Containment owner, control scope, recovery authority, last drill, and known-good version.
  • Dependencies, reusable components, version, and retirement date.

Continuous reconciliation

  • Compare Agent 365 registry records to Agent Map, connected platforms, Foundry assets, repositories, gateway traffic, and logs.
  • Flag agents with no owner, stale owner attestation, or unapproved tools.
  • Detect production traffic from development or unregistered agents.
  • Report portfolio health by business unit, risk tier, cost, and reuse.
Management answer: we know what agents we have because Agent 365 provides the inventory surface, every production agent has an Entra Agent ID-bound passport, and the platform continuously reconciles declared inventory against runtime reality.
Microsoft Entra Agent ID deep dive
Agent identity

Agent ID is the missing audit boundary.

Agent governance needs to answer which agent acted, under whose authority, and what that agent was allowed to access. Microsoft Entra Agent ID gives agents their own identity so actions can be authorized, revoked, and traced at agent level.

What Agent ID answers

  • Which agent performed the action?
  • Under whose delegated authority?
  • Which tools and resources could it access?
  • Can the agent identity be disabled or revoked?

What to bind

  • Agent 365 registry record.
  • Entra Agent ID.
  • Tool/resource permissions.
  • User delegation or service authorization.
  • Trace and audit correlation IDs.

Crawl

Inventory and minimum controls

Goal: create visibility and stop unmanaged growth. Do this before trying to build a perfect governance platform.

Timebox: 30-60 days Primary owners: platform + security Audience: every agent-building team
  1. 1. Name the accountable owners.Assign a business owner, technical owner, platform owner, security owner, and tool owner role. Publish who approves each risk tier and who responds to incidents.
    Read more

    Name owners for every governance object, not only for the agent record. A reusable blueprint can have one owner, while every instantiated agent still needs its own business and technical accountability.

    • Governance team: executive sponsor, platform owner, security/compliance owner, and operating cadence. Source: Build a cloud governance team.
    • Agent instance / Agent ID: business owner, technical owner, risk owner, support contact, and escalation path.
    • Blueprint or template: blueprint product owner responsible for default controls, docs, evals, versioning, and deprecation.
    • Agent identity and access: Entra Agent ID owner, app/service principal owner where applicable, security group owner, and RBAC assignment owner. Sources: Microsoft Entra Agent ID, Assign enterprise application owners, and Foundry RBAC.
    • Data, tool, and runtime owners: data owner for each source, tool owner for every callable tool, and platform/runtime owner for the hosting environment.
  2. 2. Define the agent passport.Create the mandatory metadata record: purpose, owner, users, data sources, tools, model/provider, environment, identity, risk tier, evals, guardrails, support contact, and retirement date.
    Read more

    The passport is the minimum registry record that lets governance, security, and operations answer: what is this agent, who owns it, where does it run, what can it access, and what evidence proves it is controlled?

Walk

Automated gates and runtime policy

Goal: move governance from documents and meetings into repeatable platform controls.

Timebox: 60-120 days Primary owners: platform engineering + app teams Audience: product teams and developers
  1. 1. Put tool calls behind runtime enforcement.Route sensitive tool calls through Foundry controls, APIM GenAI Gateway, a tool gateway, MCP policy layer, workflow gate, ACA-hosted service, or custom enforcement layer that checks Agent ID, scope, policy, approval, rate limits, and audit requirements.
    Read more

    Start with tools that can write, send, delete, change access, spend money, or call external systems. Put those behind an enforcement point before expanding to lower-risk tools.

    • Onboard AI model, agent, MCP, and A2A endpoints through an AI gateway where possible. Source: AI gateway capabilities in Azure API Management.
    • Check caller identity, Entra Agent ID, tool name, resource scope, risk tier, approval requirement, and rate/token budget before execution.
    • Log allow/deny/approval-required decisions as audit events, not only API access logs.
    • For Foundry agents, align endpoint access with Foundry roles and agent scopes. Source: Microsoft Foundry RBAC.
  2. 2. Turn risk tiers into policy-as-code.Encode what each tier requires: approved data sources, allowed models, required guardrails, human approval thresholds, eval minimums, and logging retention.
    Read more

    Write policy in a form that can be evaluated automatically in CI/CD and again at runtime.

    • Define policy requirements per tier: allowed data classes, allowed tools, approval requirements, eval thresholds, logging retention, and exception rules.
    • Use Azure Policy for Azure resource standards and compliance reporting where applicable. Source: Overview of Azure Policy.
    • Use gateway policy for runtime traffic controls such as authentication, authorization, quotas, routing, logging, and token limits. Source: AI gateway capabilities.
    • Keep policy decisions explainable: every denial or approval pause should cite the rule, agent, user, tool, target resource, and evidence.
  3. 3. Make evals a release gate.Use Foundry evals or equivalent suites for task success, groundedness, tool-call correctness, safety, jailbreak resistance, data leakage, and regression after prompt/model/tool changes.
    Read more

    Each agent needs a repeatable eval suite before production and after changes to the prompt, model, tools, data sources, policies, or blueprint.

    • Use Foundry observability capabilities for evaluation, monitoring, and tracing. Source: Observability in Generative AI.
    • Include quality metrics, RAG metrics, safety/security metrics, and agent-specific metrics such as tool-call accuracy and task completion.
    • Add Azure AI Content Safety or equivalent checks for harmful user-generated and AI-generated content. Source: Azure AI Content Safety overview.
    • Store eval run ID, dataset version, threshold, pass/fail, owner, and release decision in the agent passport.
  4. 4. Certify the first reusable tools.Pick the top duplicated tools, define schemas and permission scopes, add tests and telemetry, assign owners, and publish them in a catalog with usage examples.
    Read more

    Start with the tools many agents duplicate: ticket lookup, knowledge search, CRM read, incident status, message draft, approval request, or service restart.

    • For each tool, publish owner, purpose, schema, authentication method, required roles, allowed scopes, side-effect class, idempotency behavior, test evidence, and deprecation path.
    • Expose existing REST APIs as MCP servers only after ownership, auth, logging, and policy are clear. Source: AI gateway capabilities.
    • Use Foundry RBAC and Entra ownership to separate builders, consumers, and privileged publishers. Sources: Foundry RBAC and Entra app owners.
  5. 5. Add approval workflows for side effects.Require exact approval for high-impact writes, customer communications, financial actions, privilege changes, and production operations.
    Read more

    Approval should bind to the exact proposed action, not a broad permission like "let the agent proceed."

    • Capture approver, role, timestamp, expiry, target resource, tool name, normalized arguments, risk tier, and action digest.
    • Require approval for Tier 3+ actions such as production writes, customer-visible messages, financial transactions, access changes, and destructive operations.
    • Revalidate the approval at the gateway immediately before the side effect; do not trust only the agent-side precheck.
    • Use Entra groups or app roles to define who can approve each class of action. Source: Entra application ownership.
  6. 6. Connect observability to portfolio views.Create dashboards by business unit, owner, risk tier, tool usage, cost, policy failures, eval status, incidents, and reuse.
    Read more

    Operational telemetry should roll up into portfolio governance, not just individual application dashboards.

    • Trace LLM calls, retrieval, tool invocations, agent decisions, latency, token consumption, errors, quality scores, and policy decisions. Source: Foundry observability.
    • Use Application Insights/Azure Monitor for operational dashboards, alerts, traces, and logs. Source: Application Insights overview.
    • Dashboard by owner, business unit, risk tier, blueprint, tool, model/provider, environment, and exception status.
  7. 7. Create exception handling.Define how teams request exceptions, who approves them, when they expire, and how they are visible in audit and owner attestation.
    Read more

    Exceptions are normal, but unmanaged exceptions become the new shadow estate.

    • Require exception owner, policy waived, business justification, risk acceptance, compensating controls, expiry date, and renewal process.
    • Display active exceptions in the passport and portfolio dashboard so they are visible during attestation.
    • Use the governance team's authority and compliance-monitoring function as the operating model. Source: Build a cloud governance team.
  8. 8. Build the developer golden path.Provide templates, CI/CD checks, registry automation, sample policies, approved tools, eval harnesses, and deployment gates.
    Read more

    The golden path should make the compliant path faster than the custom path.

    • Provide starter templates for each approved pattern, prewired to Agent 365 registry metadata, Entra Agent ID, logging, evals, and runtime policy.
    • Use Foundry project roles to separate project managers, builders, publishers, and consumers. Source: Foundry RBAC enterprise mappings.
    • Automate passport creation, role checks, eval execution, and release evidence collection in CI/CD.

Exit criteria: new production agents pass automated gates, sensitive tools are gateway-controlled, eval evidence is attached to releases, and portfolio dashboards show live governance health.
