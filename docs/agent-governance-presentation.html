Enterprise agent governance

Govern 10,000 agents without slowing every team down.

Agent governance is portfolio management, runtime control, and software supply-chain discipline brought together. The goal is not to block autonomy; it is to make autonomy discoverable, reusable, observable, and safe enough to scale.

Why this is different

Agents are not just applications with a chat UI.

They plan, call tools, use data, make decisions, and can change systems. That makes the governance problem broader than app inventory or model safety alone.

Inventory drift

Teams create agents faster than central teams can track them. Unknown agents create unknown risk.

Duplicated capability

Many agents repeat the same tools, prompts, and workflows because there is no certified reuse path.

Runtime opacity

Without traces across prompts, policy, tool calls, approvals, data access, and outcomes, governance becomes manual archaeology.

Operating model

Govern the full lifecycle, not just deployment.

The enterprise pattern is a repeatable loop: discover, register, classify, approve, run, observe, reuse, and retire.

Discover

Find agents across builders, platforms, and telemetry

Combine A365 or agent registry records, Foundry assets, code repositories, gateway traffic, and observability signals to detect both registered and shadow agents.

Register

Bind every agent to ownership and identity

Require business owner, technical owner, purpose, environment, managed identity, data sources, tools, model/provider, and support path before production use.

Classify

Use risk tiers instead of one-size-fits-all gates

Tier by autonomy, data sensitivity, tool power, external exposure, user population, and business criticality.

Approve

Turn policy into automated gates

Use policy-as-code, required evals, security review, tool certification, and explicit approvals for higher-risk capabilities.

Run

Enforce at runtime, not only at design time

Use identity, GenAI gateway controls, guardrails, tool-call policy, rate limits, DLP, approvals, and kill switches.

Observe

Trace decisions from prompt to outcome

Capture prompt, plan, retrieved data, policy decision, tool call, approval, cost, latency, output, and user feedback.

Reuse

Publish proven agents, tools, prompts, and patterns

Create a catalog where teams can reuse certified components with versioning, ownership, docs, and evidence.

Retire

Remove stale agents before they become unmanaged risk

Use lifecycle dates, usage telemetry, owner attestation, dependency checks, and deprecation policies.

Inventory and ownership

Knowing what agents you have requires both registration and detection.

A registry tells you what should exist. Telemetry and gateway logs tell you what actually exists.

Minimum agent passport

  • Business owner, technical owner, and support contact.
  • Purpose, users, environment, lifecycle state, and value hypothesis.
  • Managed identity, model/provider, data sources, tools, and permissions.
  • Risk tier, required approvals, eval suite, guardrails, and audit retention.
  • Dependencies, reusable components, version, and retirement date.

Continuous reconciliation

  • Compare registry records to Foundry assets, repositories, gateway traffic, and logs.
  • Flag agents with no owner, stale owner attestation, or unapproved tools.
  • Detect production traffic from development or unregistered agents.
  • Report portfolio health by business unit, risk tier, cost, and reuse.
Management answer: we know what agents we have because every production agent has an identity-bound passport, and the platform continuously reconciles declared inventory against runtime reality.

Reuse and marketplace

Govern tools as products, not one-off code snippets.

The fastest way to scale safely is to make the approved path easier than rebuilding. That means certified tools, reusable templates, and clear ownership.

Certified tool catalog

Each tool has an owner, schema, permissions, policies, examples, evals, version, changelog, and deprecation plan.

Reusable agent patterns

Publish golden patterns for knowledge agents, workflow agents, approval-based agents, and operational agents.

Evidence travels with components

Reuse includes proof: eval scores, red-team results, policy coverage, data classification, and known limitations.

Developer answer: reuse works when tools and agents are published like internal products: discoverable, versioned, documented, tested, owned, and policy-ready.
Runtime enforcement

Design-time review is not enough for agentic systems.

Runtime controls must see the full path: user request, prompt, retrieved context, model output, planned action, tool call, approval, and result.

RequestUser or workflow trigger

Authenticated user, business process, or scheduled event.

ReasonAgent runtime

Model, prompt, memory, retrieval, planning, and tool selection.

CheckPolicy and guardrails

Safety, DLP, data boundaries, jailbreak checks, and action policy.

ApproveHuman or automated gate

Exact approval for high-impact actions, budgets, and exceptions.

ExecuteGoverned tool gateway

Revalidate identity, scope, policy, approval, and audit before side effects.

Runtime enforcement should be close to the side effect. If a tool can change a system, the gateway must re-check authorization, policy, approval, and blast radius even if the agent already checked earlier.
Evaluation and observability

Trust is maintained through continuous evidence.

Evals and observability should become release gates, operational dashboards, and audit evidence, not ad hoc notebooks.

Before release

  • Scenario and task-completion evals.
  • Safety, jailbreak, and data-leakage tests.
  • Tool-call accuracy and policy coverage.

During runtime

  • Prompt, plan, policy, tool, approval, and outcome traces.
  • Latency, cost, error, escalation, and fallback metrics.
  • Alerts for drift, anomalous tool usage, and policy failures.

After change

  • Regression evals on model, prompt, tool, and policy changes.
  • Owner attestation and risk-tier review.
  • Incident review and catalog evidence updates.

Roles and accountability

Agent governance needs clear ownership across business and engineering.

Central teams enable and enforce. Business and product owners remain accountable for purpose, value, and acceptable risk.

Business owner

Defines purpose, value, acceptable risk, user scope, and lifecycle.

Technical owner

Owns implementation, dependencies, tool use, evals, and operations.

Platform team

Provides registry, templates, gateway, observability, and paved roads.

Security and compliance

Defines policies, risk tiers, exceptions, audit needs, and guardrails.

Tool owner

Certifies tool contracts, permissions, tests, versions, and deprecation.

Data owner

Approves data use, classification, retention, and DLP requirements.

SRE or operations

Owns runtime health, incidents, alerts, cost, and reliability.

Governance board

Sets standards, handles high-risk approvals, and reviews portfolio health.

Maturity roadmap

Start with visibility, then add automation, then scale reuse.

The first milestone is not perfect policy. It is a trusted inventory and a paved road that teams actually want to use.

Crawl

Inventory and minimum controls

  • Define agent passport and risk tiers.
  • Inventory known agents and tools.
  • Require owner, identity, and basic logging.
  • Publish initial policy and approved patterns.
Walk

Automated gates and runtime policy

  • Adopt gateway controls for tool calls.
  • Make evals part of release promotion.
  • Launch reusable tool catalog.
  • Connect observability to portfolio reporting.
Run

Portfolio optimization and reuse at scale

  • Automate drift detection and owner attestation.
  • Certify agent templates and tool products.
  • Use risk-based automated approvals.
  • Measure reuse, cost, safety, and business impact.

The target state: every agent is known, owned, risk-tiered, observable, and reusable.

That is how enterprises move from isolated agent experiments to a governed agent ecosystem.
